# 담당자에게 조건 확인하기

불완전한 문제를 보완하는 **업무 질문**을 준비하라. 질문 수가 아니라 중요한 불확실성이 실제로 해소됐는지 확인하라. 과제 안내·기존 규칙·사용자 요청을 먼저 따르고, AI 사용이 금지된 단계에서는 중단하라.

## 1. 읽고 구분하라

- 문제문·README·제공 데이터의 스키마/작은 표본·현재 작업 기록·실제 담당자 답변을 필요한 만큼 확인하라. 이미 답이 있는 내용을 다시 묻지 마라. 데이터의 관찰된 최대값을 운영 최대 규모나 정책으로 확정하지 마라.
- 관련 조건을 **문제에 명시 / 담당자 확인 / 사용자 설계 선택 / 임시 가정 / 미확인 / 충돌**로 구분하라. 구현 제한이나 AI 추천을 업무 조건으로 옮기지 마라.
- 기존 WORKLOG 등 정본 하나에 필요한 행만 추가하라. `explain-as-you-build`가 사용 중이면 그 정본을 공유하라. 담당자용 문서·질문 원장·개발 원장을 따로 늘리지 마라.
- 숨은 조건의 존재·개수·출제 빈도·질문 여부의 배점은 실제 안내 없이는 미확인이다. 특정 조건을 알아내면 점수가 오른다고 보장하지 마라. 연습의 평가자용 비공개 시나리오·정답 파일을 풀이나 질문을 만드는 근거로 읽지 마라.

## 2. 구현을 바꿀 빈틈부터 찾아라

[질문 후보와 기록](references/questions.md)의 축 중 현재 문제와 관련된 것만 점검하라. 먼저 전체 결과를 뒤집는 불확실성과 잘못 구현하면 되돌리기 큰 가정을 찾고, 작은 표현·일반 취향은 뒤로 미뤄라.

- 각 후보에 **현재 근거 / 모르는 조건 / 답에 따라 달라질 설계·완료 판정 / 물을 대상**을 붙여라. 관련 없거나 이미 확인한 축은 생략하라.
- 업무 목표·우선순위·예외·데이터 의미는 가상 업무 담당자에게, 환경 사용·도구·제출 규정은 제공된 도우미/과제 안내에 확인하라. 기술 구현 선택은 확정 업무 조건 아래 사용자에게 비교하라.
- 예컨대 '모두 배정'이 목표인지, 불가능하면 일부 미배정을 허용하는지에 따라 알고리즘 선택 자체가 달라진다. 먼저 업무 목표를 확인하고 설계 대안 비교로 넘겨라.
- 도구 없이 읽을 수 있는 명세·스키마·기존 답을 먼저 확인하되, 기술적 관찰로 담당자가 정할 업무 정책을 대신 확정하지 마라.

## 3. 짧게 묻고 실제 답을 받아라

- 처음에는 영향이 큰 **최대 3개 질문**을 우선하라. 한 질문은 하나의 결정에 집중하고, 왜 필요한지 한 문장으로 설명하라. 필요한 후속 질문은 앞 답을 보고 만들라. 독립적인 질문은 짧게 묶을 수 있다.
- '숨은 조건을 전부 알려주세요'나 일반 점검표 전체를 보내지 마라. 원하는 답을 유도하지 말고 중립적으로 물어라. 실제로 해석이 갈리는 경우에만 대비되는 예와 경계값으로 의미를 확인하라.
- 질문에 Q1 같은 식별자를 주고 **작성 / 실제 전송 / 답 수신 / 일부 미해결**을 구분하라. 질문 초안을 보여준 것은 담당자에게 물은 것이 아니다.
- 현재 제공된 가상 담당자에게 질문하는 기능이 있고 사용자가 질문 수행을 맡긴 경우에만 그 허용 경로로 보낼 수 있다. CLI만 있고 메신저 접근이 없으면 사용자가 그대로 보낼 짧은 문장을 주고 실제 답을 기다려라. 사용자 승인 없는 실제 사람·메일·Slack 등으로 대신 연락하지 마라. 실제 수신 답이 없으면 담당자 답을 연기하거나 만들어내지 마라.
- '적당히', '가능하면', '기존대로' 같은 답은 해당 결정에 필요한 수치·우선순위·구체 예 하나로 좁혀라. 동의나 짧은 '네'를 질문하지 않은 조건까지 확대하지 마라. 모른다고 한 항목은 미확인으로 유지하라.

## 4. 답을 실행 기준으로 바꿔라

- 실제 답의 발화/메시지 위치·Q ID·답 요지를 보존하고 **확정된 조건 → 바뀐 설계/입력 처리 → 완료 기준/검증**을 연결하라. 수치·시각·인간 판단·질문 이력을 꾸미지 마라.
- 일부만 답했으면 해결된 항목만 확정하고 나머지는 열어둬라. 새 답이 기존 문제문·답변과 충돌하면 두 출처와 대상 범위를 나란히 확인하라. 더 늦은 답이라는 이유만으로 규정·제출 지침까지 덮어쓰지 마라. 담당자의 업무 권한과 도구/보안 규정 변경 권한을 구분하라.
- 담당자가 방법 선택을 명확히 맡긴 범위만 **설계 재량**으로 구분하라. 이것은 AI의 자동 결정이나 사용자의 선택이 아니다. 중요한 설계는 사용자에게 대안을 비교하고 선택 후 구현하라.
- 기존 사용자 선택은 유효한 전제가 유지되면 재확인하지 마라. 새 조건 때문에 성립하지 않으면 영향과 대안을 알리고 해당 선택만 다시 확인하라. 기존 코드를 새 조건에 맞는 것으로 표시하지 마라.

## 5. 진행 경계를 정하고 넘겨라

- 정확성·필수 제약·핵심 우선순위·중대한 데이터 손실을 바꾸는 미확인은 그 조건에 의존하는 설계 확정·구현을 보류하라. 자료 확인·독립 작업·영향 분석은 계속할 수 있다. 확인 없이 기술 스택·알고리즘·영구 저장 정책부터 고정하지 마라.
- 낮은 위험이며 되돌릴 수 있는 미확인은 임시 가정·영향·후속 확인을 명시하고 독립 작업을 진행할 수 있다. 반드시 확정할 조건을 임시 가정으로 몰래 우회하지 마라.
- 남은 시간이나 담당자 응답 제한이 있으면 큰 영향을 주는 질문부터 보내고, 답을 못 얻은 조건과 제출 시 한계를 기록하라. 응답이 없다고 묵시적으로 승인됐다고 쓰지 마라.
- 핵심 판단에 필요한 조건이 충분하고 남은 미확인이 제한적이면 질문을 멈춰라. 모든 잠재 조건을 다 찾아냈다고 주장하지 마라. 새 자료·실패·조건 변경 때 영향받은 부분만 다시 확인하라.
- 마지막에는 **확인된 핵심 조건 / 남은 위험한 미확인 / 다음 질문 또는 진행 가능한 결정**만 짧게 보여라. 설계 비교·구현·설명은 `explain-as-you-build`, 검증 준비는 `guide-manual-tests`로 연결하되, 이 스킬들 없이도 조건 기록과 질문 준비는 가능해야 한다.
