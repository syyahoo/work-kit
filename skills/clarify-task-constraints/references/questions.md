# 질문 후보와 기록

체크리스트 전체를 전송하지 마라. 아래에서 현재 문제의 결과·설계를 바꾸는 미확인만 골라라. 예시는 일반 질문 틀이며 시험 기출·숨은 정답이 아니다.

| 축 | 알아야 할 차이 | 중립적인 질문 예 |
|---|---|---|
| 사용자·업무 목표 | 누가 어떤 판단·행동을 하는가 | 결과를 누가 사용하며, 무엇이 개선되면 성공인가요? |
| 우선순위·절충 | 절대 지킬 조건과 개선 목표 | 두 목표를 동시에 만족할 수 없다면 무엇을 먼저 지켜야 하나요? |
| 자원·실행 불가능 | 정원·재고·예산 부족의 처리 | 조건을 모두 만족할 수 없을 때 허용되는 결과와 사용자 안내는 무엇인가요? |
| 배정·순서·공정성 | 선택 가능 범위·동률·우선 대상 | 같은 조건의 신청자가 경쟁하면 적용할 업무상 우선순위가 있나요? |
| 데이터 의미·정합성 | ID·중복·결측·단위·기간 | 동일 ID가 여러 번 나오면 같은 건의 변경인가요, 별도 건인가요? |
| 규모·시간 | 표본과 실제 규모·응답 허용치 | 실제 최대 처리 규모와 결과를 기다릴 수 있는 시간은 어느 정도인가요? |
| 저장·동시 사용 | 새로고침·재시작·공유·적용 단위 | 누가 동시에 쓰며, 어떤 시점까지 결과가 보존되어야 하나요? |
| 취소·변경·실패 | 처리 전·중·후의 상태와 복구 | 처리 중 취소하거나 입력이 바뀌면 이미 반영된 내용은 어떻게 취급하나요? |
| 결과·완료 기준 | 필수 출력·설명·재현·제출 형식 | 필수 결과와 완료를 판단할 확인 사례는 무엇인가요? |

'저장은 localStorage면 되죠?'처럼 수단으로 유도하지 말고, 필요한 보존·공유 조건을 먼저 물어라. 데이터가 작다는 이유만으로 최대 규모 질문을 생략하거나, 단순 시연이라는 이유만으로 업무 정확성을 생략하지 마라.

## 기존 정본 안의 짧은 행

| Q·상태 | 질문·대상 R | 실제 답·출처 | 해석·미확인 | 관련 D·코드·T에 미치는 영향 |
|---|---|---|---|---|

- 답이 없으면 '답 없음'으로 쓴다. 표를 채우려고 대답을 만들지 마라.
- 문서에 원래 있던 조건은 그 문서 위치를 출처로 적고, 담당자에게 질문해 얻었다고 바꾸지 마라.
- 복수 조건을 포함한 답은 항목별로 범위를 나눈다. 답이 일부만 해결하면 질문 전체를 완료로 표시하지 마라.
- 답을 구현한 것과 검증한 것은 별개다. 예상 결과를 실제 실행 결과로 쓰지 마라.

## 새 답을 받은 뒤의 짧은 설명

> Q[번호]에서 [실제 답]을 확인했습니다.
> 따라서 [조건]을 적용하며 [설계·완료 기준]이 달라집니다.
> 아직 [미확인]은 남아 있어 [의존 작업]은 보류하거나 [명시한 임시 가정의 독립 작업]만 진행합니다.

검증 사례의 구체적인 입력은 확인된 조건에서 도출하라. 존재하지 않는 정답 수치·평가 기준을 덧붙이지 마라.
