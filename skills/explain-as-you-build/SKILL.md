# 작업하며 이해하기

작업을 수행하면서 사람이 결과의 원리와 판단 근거를 이해하게 하라. 과제 지침·기존 프로젝트 규칙·사용자 요청을 먼저 따르라. 이 문서를 읽었다는 사실을 자동 등록, hook 설치, 후속 턴의 자동 실행 성공으로 표현하지 마라.

## 시작과 재개

1. 실제 작업 디렉터리, 요구사항, 기존 코드·기록, 실행 도구를 필요한 범위만 확인하라. 확정된 내용은 다시 묻지 마라. 목표·필수 제약·업무 우선순위·실제 규모 등 결과를 바꾸는 조건은 담당자 답과 임시 가정을 구분하고, 확인 전에 기술 스택·알고리즘·저장 정책부터 고정하지 마라. `clarify-task-constraints`가 있으면 조건 확인에 사용하라. 없으면 중요한 질문을 짧게 준비하고 실제 답을 기록하라. 핵심 미확인이 막는 의존 구현은 보류하고 자료 확인·독립 작업은 계속하라.
2. 기록할 **하나의 정본**을 선택하라. 기존 WORKLOG나 프로젝트 기록을 우선하라. 없을 때만 [기록 양식](assets/worklog-template.md)을 작업 폴더의 `WORKLOG.md`로 사용하라. 설치 폴더에 과제 기록을 쓰거나 기존 파일을 통째로 교체하지 마라.
3. 필수 완료 조건에 자료·관련 함수·확인 방법을 연결하라. 과제가 정한 제출 파일명·위치를 바꾸지 마라.
4. 재개할 때 기록과 실제 변경 파일을 대조하라. 이전 결과와 최신 상태를 구분하고 영향받은 근거만 재확인하라. 새 세션에는 이 SKILL.md와 선택한 정본의 경로를 함께 읽도록 안내하라.

기본은 구현·분석을 계속하는 **작업 동행**이다. 중요한 설계는 아래 비교·선택 절차를 따르되, 단순 코드 정리·기존 선택의 구현까지 매번 승인받지 마라. 문답·이해도 점수로 작업을 멈추지 마라. 설명만 요청받으면 읽기 전용으로 설명하라.

## 설계 대안 비교와 사용자 선택

저장 방식, 핵심 알고리즘·우선순위, 상태·동시성 처리, 정확도와 처리시간의 절충처럼 결과·제약·유지 비용을 바꾸는 **중요한 설계 결정은 구현 전에** 다음 절차를 수행하라. 사용자가 특정 결정을 비교해 달라고 하면 그 결정도 포함하라.

1. 실제 요구·현재 환경·남은 시간을 확인하고 실행 가능한 대안 2~3개를 마련하라. 가능한 경우 가장 단순한 방식이나 현재 방식을 포함하라. 추천안을 돋보이게 할 허수 대안, 불필요한 복잡성, 필수 제약을 어기는 안을 선택지로 넣지 마라. 실질적인 안이 하나뿐이면 제약과 제외 이유를 밝히고 수용 또는 제약 변경 의사를 확인하라.
2. 전문용어를 풀어서 **선택지 / 처리 방식 / 장점 / 단점·취약 조건 / 현재 과제와의 적합성** 표로 나란히 보여라. 예측 성능·구현 부담은 추정임을 밝히고 실행 수치처럼 쓰지 마라. 정보가 부족하면 비교에 영향을 주는 불확실성을 표시하라.
3. 추천안과 근거를 별도로 짧게 제시하고 **사용자에게 어느 안을 선택할지 물어라.** 추천을 확정 결정으로 바꾸지 마라. 서로 독립적인 결정만 작은 묶음으로 질문하고, 앞선 선택에 따라 달라지는 결정은 이후에 비교하라.
4. **선택을 기다린 뒤 그 선택에 의존하는 구현·설정 변경을 진행하라.** 응답 없음·시간 경과는 선택이 아니다. 기다리는 동안 관련 자료 확인·기존 검사 등 선택에 의존하지 않는 작업은 계속할 수 있다. 특정 안을 몰래 먼저 구현하지 마라.
5. 기존 대화·정본에서 이미 선택한 안은 재확인 없이 이어가라. 주요 전제 변경이나 새 제약으로 선택이 성립하지 않을 때만 변경점·영향·대안을 다시 제시하라. 사용자가 명시적으로 판단을 위임한 범위에서는 AI가 고를 수 있으나 위임 근거와 AI 선택임을 기록하라.
6. 정본에 비교한 대안, AI 추천과 근거, 사용자 실제 선택, 선택 이유, 예상 장단점·한계, 반영 위치·검증을 연결하라. 선택 전에는 '선택 대기'로 표시하라. 이유 없이 A만 골랐다면 **'사용자 선택 A / 사용자 이유 미제공 / AI 추천 근거는 별도'**로 쓰고 구현을 진행하라. 이유를 답해야만 진행하는 시험을 만들지 마라.

## 설명·기록 시점

요구 확정, 대안 선택·방향 변경, 핵심 로직 구현, 의미 있는 검증·실패·수정, 마감·중단·재개에서 관련 기록을 갱신하라.

- 변경 묶음당 짧은 기록 하나를 남겨라. 단순 탐색·형식 변경·매 도구 호출은 기록하지 마라.
- 현재 작업에 맞는 작은 구현과 검증을 수행하라. 설명을 위해 프레임워크·MCP·패키지·대규모 테스트를 도입하지 마라.
- 기본 설명은 **이번 결과 → 처리 원리 → 선택 이유 → 확인 범위·한계** 순서로 한국어 4~8문장으로 하라. 코드 위치는 이해에 필요한 만큼만 제시하라.
- 선택·원리·위험이 그대로면 전체 설명을 반복하지 마라. 진행 중 질문에는 관련 답을 먼저 주고 작업을 이어가라.

## 네 가지 설명 축

### 실제 동작과 예외

사용자 행동에서 데이터 변경·결과 표시까지 추적하라. 현재 구현에 관련된 취소·중복 실행·처리 중 입력 변경·실패·새로고침만 골라라. 필요한 기준은 [변경 상황 점검](references/change-checks.md)에서 읽어라.

- 취소를 적용 전/진행 중/완료 후로 나눠라. 화면 닫기·요청 중단·서버 처리 중단·저장 복구는 별개다. 완료된 저장을 취소 버튼만으로 되돌릴 수 있다고 가정하지 마라.
- 이전 입력의 늦은 응답이 최신 결과를 덮는지, 실패 때 일부 데이터만 남는지, 중복 요청·재시도가 부작용을 반복하는지 확인하라.
- 버튼 비활성화만으로 서버의 중복 처리 방지·데이터 일관성을 증명하지 마라. 순차 실행을 동시성 검증이라고 쓰지 마라.
- 예상 동작·현재 관찰·아직 구현하지 않은 대응을 분리하라.

### 알고리즘과 처리 원리

현재 호출되는 코드로 **입력 → 우선순위·선택 기준 → 반복·분기 → 종료·출력**을 설명하라. CRUD처럼 이름이 중요하지 않으면 데이터 흐름·검증 규칙을 설명하라.

- 코드가 뒷받침할 때만 탐욕법·탐색·최적화 등의 이름을 붙여라. 라이브러리 이름으로 대신하지 마라.
- 작은 합성 입력 하나를 실제 구현에 따라 추적하라. 선택 이유, 동점 처리, 배정 불가·오류 처리를 연결하라. 예시 통과는 일반성·최적성의 증명이 아니다.
- 목표 함수와 필수 제약, 유효한 결과와 개선된 결과와 전역 최적 결과를 구분하라. 최적성 보장 근거가 없으면 명시하라.
- 성능이 중요할 때 n·m의 뜻과 실제 반복·탐색 근거를 적어라. 측정 시간과 이론 복잡도를 구별하라. 하위 호출을 확인하지 못하면 미확인으로 남겨라.

### 제약과 개선

관련된 변화만 **조건 변화 → 먼저 깨지는 부분 → 사용자 영향 → 대응 → 확인 방법**으로 설명하라.

- 필수 자원 부족의 실행 불가능성, 조건 누락·잘못된 결과의 정확성, 느린 계산·화면의 성능, 나쁜 배정·경로의 결과 품질을 구별하라.
- 총량이 충분하다고 개별 제약 충족을 단정하지 마라. 필수 제약을 몰래 완화해 성공시키지 마라.
- 규모 검증은 기존 크기와 더 큰 합성 입력의 정합성·실행시간을 비교하라. 실행하지 않았다면 예상·측정 계획만 적어라. 예측 시간을 측정값으로 쓰지 마라.
- 현재 결함의 최소 수정부터 검토하라. 미적용 개선은 현재 기능으로 설명하지 마라.

### AI 제안과 사람의 판단

실제 대화·변경·실행 기록에서 **최초 제안 → 결정 주체와 변경 지시 → 이유 → 반영 위치 → 결과**를 찾아라.

- AI 자기 수정, 사용자의 구체적 개입, 담당자가 확정한 정책을 구분하라. 일반적인 'AI 검토'를 구체적인 인간 판단으로 확대하지 마라.
- 기록이 없으면 '기록 없음/확인 필요'로 남겨라. 사용자 개입을 만들어내거나 점수를 위해 변경을 유도하지 마라.
- 이유가 필요하면 중립적으로 확인하라. 기록 없는 이유를 대신 만들어 넣지 마라.

## 검증 근거

1. 요구·위험에 맞는 기존 명령, 작은 검사, 허용된 직접 조작을 골라라. 저위험 변경에 불필요한 테스트를 만들지 마라.
2. **입력/조건·기대·실제 결과·명령/절차·대상 코드 상태**를 기록하라. 커밋과 미커밋 변경 또는 관련 파일 해시로 판본을 식별하라. 확인한 범위 이상으로 재현성을 주장하지 마라.
3. 정적 코드 확인 / 실제 실행 / mock / 사용자 관찰 / 추정 / 미검증을 구분하라. 타 에이전트의 보고를 직접 실행으로 바꾸지 마라. 브라우저가 없으면 로직 검사와 미확인 UI 경계를 구분하라.
4. 실행 0건·전부 skip·실패한 명령·옛 코드의 통과를 현재 통과로 쓰지 마라. 출력·실패 수·종료코드를 실제 확인하라. 제공되지 않은 종료코드를 만들지 마라.
5. 결함은 같은 재현 조건의 실패와 수정 후 결과를 연결하라. 검사·입력·기대값이 바뀌면 새 기준임을 밝혀라. 실패 이력·인간 판단·기록 시각을 꾸미지 마라.
6. 컴파일 성공은 업무 정확성·예외 처리를 증명하지 않는다. 출력과 코드가 어긋나면 차이를 먼저 해결하거나 불확실성을 남겨라.

## 짧고 현재 상태인 정본

새 발견이 있는 축만 추가하라. 관련 없는 축은 이유와 함께 한 번만 해당 없음으로 표시하라. 중요한 이전 결정·실패 근거는 보존하고 후속 기록으로 정정하라. 최신 요약은 갱신할 수 있지만 이력은 지우지 마라.

한 사건에 다음을 짧게 기록하라. 존재하지 않는 수치·경로를 채우지 마라.

> 변경: 무엇이 달라졌는가 / 대상 파일·판본
> 판단: 비교안·AI 추천과 근거·사용자 선택 또는 대기·이유의 실제 출처
> 원리: 선택 기준·처리 순서·관련 함수
> 검증: 조건·기대·관찰·절차·증거 종류
> 한계: 발생 조건·영향·미검증·다음 확인

마감 전 코드와 기록의 모순, 근거 없는 완료 표시, 남은 필수 요구를 대조하라. 개선 우선순위를 짧게 설명하라. 파일 전체 재독과 같은 검사 재실행을 이유 없이 반복하지 마라.

## 선택적 문답과 이식

- 연습문제 준비·출제·채점을 요청받으면 [서술형 출제 기준](references/essay-practice.md)을 읽어라. 실제 판본과 근거를 확인하고 유형·문항·채점 기준을 연결하라. 자료 정리 요청만으로 문답을 시작하지 마라.
- 요청받을 때만 실제 구현·기록에서 질문 한 개를 내고 답을 기다려라. 사실 오류 하나와 보완할 근거 하나에 집중하라.
- 독립적으로 읽는 Markdown만 요구하라. 외부 API·MCP·hook·특정 프레임워크는 필수 의존성이 아니다. 타 환경에서는 이 파일의 정확한 경로를 명시해 읽게 하라. 등록과 실행 성공을 실제 관찰로 확인하라.
