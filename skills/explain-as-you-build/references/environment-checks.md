# 문서 중심 웹 IDE와 Docker 실행 점검

완성된 앱·Docker 설정이 제공된다고 가정하지 마라. 먼저 실제 파일과 도구를 확인하라. Docker 사용 경험은 사용 가능성의 근거일 수 있으나 필수 규정이나 현재 daemon 가동의 증거가 아니다. 핵심 업무 조건이 미확인인 동안에는 읽기·실행 가능성 점검만 하고 그 조건에 의존하는 프레임워크·서버·DB를 확정하지 마라.

## 환경 확인과 구성

- 실제 작업 경로·README·입력 파일, 기존 Dockerfile·Compose·실행 스크립트가 있는지 확인하라. 있으면 읽고 재사용 여부를 판단하고, 없으면 확정된 설계에 맞는 최소 설정을 작성하라.
- `docker version`의 client와 server 연결을 구분하고, 필요한 경우 `docker compose version`을 확인하라. 명령 존재만으로 Docker 실행 성공을 표시하지 마라. Docker가 없거나 막혔을 때 플랫폼 설정을 임의로 바꾸는 대신 오류와 제공된 문의 경로를 사용하라.
- 컨테이너 내부 주소·포트와 공개한 호스트 포트를 구분하라. EXPOSE만으로 미리보기 연결이 되는 것은 아니다. 서버의 bind 주소, 포트 매핑, 실행 중 프로세스, 실제 로그와 IDE Browser의 포트·경로를 대조하라. 플랫폼 예시 포트를 고정 규칙으로 쓰지 마라.
- 실제 실행 환경이 Docker라면 의존성 설치·검사·실행 위치를 표시하라. 호스트에서 통과한 검사를 컨테이너 실행 검증으로 바꾸지 마라. 기록에는 소스 판본, 이미지 식별자, 실제 명령·작업 위치·접속 포트를 필요한 만큼 연결하라. 로그에 비밀값이 있으면 노출하지 마라.
- 코드 변경이 bind mount로 즉시 반영되는지, 이미지 COPY 때문에 재빌드가 필요한지 확인하라. 이전 이미지나 다른 포트의 서버를 현재 코드 결과로 착각하지 마라. 실제 보존 요구가 있을 때만 volume·DB·저장 위치를 정하라.

## 첫 화면 확인을 뒤로 미루지 마라

첫 의미 있는 화면을 만든 직후, 또는 핵심 화면·자산·라우팅·이미지/실행 설정이 바뀐 뒤에는 실제 렌더링 경계를 확인하라. 화면이 보이는지 확인하기 전에 UI 기능을 계속 쌓지 마라. 업무 조건 확인·독립 로직 작업까지 무조건 멈추라는 뜻은 아니다.

1. 빌드·컨테이너 상태·실제 포트·HTTP 응답으로 접속 준비를 확인한다.
2. 최종 사용 경로에서 HTML·JS·CSS가 로드되고 실제 화면이 표시되는지 확인한다. 자동 캡처나 브라우저 도구는 현재 규정에서 허용된 경우에만 사용한다. 금지 또는 미확인이면 사용자에게 IDE Browser의 포트·경로와 볼 내용을 짧게 안내한다.
3. 확인한 URL·경로·코드/이미지 판본·화면 범위·관찰 출처를 T와 관련 R에 기록한다. 렌더링 확인 전에는 화면 성공을 미검증으로 남긴다.
4. 로직·예외 검사와 남은 수동 흐름을 이어간다. 빌드·HTTP·로직 통과가 화면 통과를 대신하지 않는다. 첫 화면 통과가 등록·저장·취소 등 전체 기능 통과도 아니다.

현재 규정·제공 기능이 자동 렌더링을 허용하는지 판단할 때는 `guide-manual-tests`의 실제 출력 확인 절차를 따른다. 외부 도구 설치를 먼저 시작하지 마라.
