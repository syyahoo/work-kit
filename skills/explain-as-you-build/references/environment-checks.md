# 초기 셋업을 직접 수행하고 첫 화면까지 확인

구현 작업의 시작 절차로 적용하라. 완성된 앱·Docker 설정이 제공된다고 가정하지 마라. 사용자가 설명만 요청한 경우에는 실행하지 마라. 구현이 요청됐다면 “이 명령을 실행하면 된다”로 끝내지 말고 허용된 도구로 실제 설정·설치·실행을 수행하라.

## 1. 처음부터 환경을 점검

- 실제 작업 폴더·과제 지침·입력 자료·기존 코드·README·실행 스크립트·lockfile을 읽어라. 필요한 runtime·패키지 관리자 버전, 사용 중 포트, 미리보기 경로, 설치·네트워크·자동 렌더링 규정을 확인하라. 비밀값은 출력하지 마라.
- 기존 구성·정상 실행 프로세스가 있으면 소스와 포트를 대조해 재사용하라. 시작할 때마다 프로젝트를 다시 생성하거나 의존성을 전부 재설치하지 마라. 기존 파일·데이터를 덮어쓰거나 점유 포트의 무관한 프로세스를 종료하지 마라.
- 환경 점검은 업무 질문과 독립적으로 진행하라. 핵심 업무 조건이 미확인이면 그에 의존하는 프레임워크·서버·DB를 먼저 확정하지 마라. 모든 질문이 끝날 때까지 독립 점검까지 미룰 필요는 없다.

## 2. 필요한 선택을 끝내고 곧바로 셋업

기존 사용자 선택·명시적 판단 위임·과제의 지정 구성을 먼저 확인하라. 이미 확정된 선택은 다시 묻지 마라. 실행 방식 등 중요한 선택이 남아 있으면 현재 환경에서 가능한 대안 2~3개의 장단점·추천을 제시하고 선택을 받아라. 선택을 받으면 별도의 “셋업해줘” 요청을 기다리지 말고 다음을 직접 수행하라.

1. 기존 프로젝트를 우선 사용하고, 없으면 선택한 구성의 최소 파일·의존성 선언·실행 스크립트를 작성하라. 작업 폴더와 충돌 파일을 확인하고 빈 폴더용 scaffold 명령을 기존 프로젝트에 강제 적용하지 마라. 필요가 확정되지 않은 DB·인증·외부 서비스는 추가하지 마라.
2. 선택한 실행 위치에서 실제 의존성을 설치하라. 기존 lockfile·프로젝트 규칙에 맞는 설치 방법을 사용하고 성공 여부·종료 상태를 확인하라. runtime 자체가 없으면 제공된 설치 방법과 권한 범위에서 필요한 구성만 설치하라. 설치 명령을 작성한 것과 설치 성공을 구분하라.
3. 최소 의미 있는 첫 화면을 작성하거나 기존 앱을 사용해 서버를 실행하라. 웹 IDE에서 요구하는 경우 `0.0.0.0`에 bind하고 플랫폼이 지정한 값 또는 충돌 없는 포트를 사용하라. 장기 실행에 적합한 제공 기능으로 프로세스를 유지하고 실제 로그·프로세스·포트·라우트를 확인하라. 로그에 나온 실제 포트와 IDE Browser에서 입력할 포트·경로를 연결하라.
4. 현재 소스가 실행 대상인지 확인하고 HTTP·필수 자산 등 접속 준비를 검사한 뒤 아래 첫 화면 확인으로 이어가라. 오류가 나면 로그에서 원인을 좁혀 수정·재실행하라. 설치나 실행 실패를 사용자가 나중에 처리할 일반 안내로 덮지 마라.
5. 실제 실행 위치·설치/시작/재시작/중지 명령·로그 위치·접속 경로·판본·결과를 기존 정본에 짧게 남겨라. 프로젝트의 기존 실행 안내가 있으면 갱신하고 중복 문서를 만들지 마라. 기록을 남긴 뒤 기능 구현으로 이어가라.

환경 제한·권한·다운로드 실패로 직접 수행할 수 없으면 실제 오류, 막힌 단계, 가능한 대안을 밝히고 독립 작업을 계속하라. 플랫폼 제한을 우회하거나 반복 설치를 강행하지 마라. 사용자에게 넘기는 것은 AI가 실제로 할 수 없는 최소 조치뿐이다. 규정 문의 초안도 실제 답과 구분하라.

## 3. Docker를 선택한 경우

Docker 경험은 필수 규정이나 현재 daemon 가동의 증거가 아니다. 직접 runtime 실행과 Docker 중 현재 요구·환경에 맞는 방식을 선택하고 Docker가 없다는 이유만으로 앱 전체를 중단하지 마라. Docker 필수 조건이 있으면 임의로 다른 방식으로 완료 처리하지 마라.

- `docker version`의 client와 server 연결을 구분하고 필요한 경우 `docker compose version`을 확인하라. 불가하면 실제 오류와 대안을 제시하라. privileged daemon·호스트 설정을 임의로 구성하지 마라.
- 기존 Dockerfile·Compose를 읽고 재사용하거나 선택된 설계에 필요한 최소 설정을 작성하라. 실제 이미지 빌드와 컨테이너 실행을 수행하고 상태·로그를 확인하라. 이미지 파일 작성만으로 Docker 셋업 완료가 아니다.
- 컨테이너 내부 bind 주소·포트와 호스트 공개 포트를 대조하라. EXPOSE만으로 공개됐다고 보지 마라. 의존성 설치·검사·실행 위치를 표시하고 호스트 검사를 컨테이너 검증으로 바꾸지 마라.
- 소스 판본·이미지 식별자·명령·접속 포트를 연결하라. bind mount인지 COPY 후 재빌드가 필요한지 확인하고 이전 이미지·다른 서버 결과를 현재 결과로 쓰지 마라. volume·DB·데이터 보존은 확정된 요구에 맞게 구성하라.

## 4. 첫 화면을 초기 셋업의 완료 조건으로 사용

첫 의미 있는 화면을 만든 직후, 또는 핵심 화면·자산·라우팅·실행 설정이 바뀐 뒤 실제 렌더링을 확인하라. 화면이 보이는지 확인하기 전에 업무 UI를 계속 쌓지 마라. 독립 조건 확인·로직 작업은 계속할 수 있다.

1. 빌드·프로세스 또는 컨테이너 상태·실제 포트·HTTP 응답으로 접속 준비를 확인하라.
2. 최종 사용 경로에서 실제 HTML·JS·CSS 로드와 화면을 확인하라. 빈 화면·로딩 고착·오류·기본 템플릿 잔류·필수 영역 누락·잘림을 확인하라. 허용된 자동 렌더링이면 기존 도구를 우선 사용하고 필요한 도구만 직접 준비·실행하라. 캡처 파일 생성만이 아니라 실제 이미지를 열어 관찰하라.
3. 자동 렌더링이 금지·미확인이면 제공된 도우미에게 구체적으로 확인하고, 그동안 사용자가 IDE Browser에서 볼 **실제 포트 / 경로 / 기대 화면 / 확인할 항목** 한 묶음만 전달하라. 서버 준비까지 사용자에게 다시 맡기지 마라. 사용자 관찰이 오기 전 화면은 미검증으로 남겨라.
4. URL·소스/이미지 판본·화면 범위·관찰 출처·실제 오류를 T와 관련 R에 기록하라. 확인 못 한 초기 콘솔 오류 등을 사용자 화면 관찰로 확인했다고 바꾸지 마라.

자동 캡처와 자동 클릭·입력의 허용 범위를 구분하라. 규정 판단과 세부 검사는 `guide-manual-tests`의 실제 출력 확인 절차를 따르라. 브라우저를 무조건 설치하거나 자동 조작 권한을 가정하지 마라.

## 5. 셋업 완료 판정

**설정 작성 → 실제 의존성 준비 → 서버 가동 → 현재 소스·경로 접속 → 첫 화면 관찰**의 각 결과를 확인하라. 필요한 항목이 실제 성공한 경우만 초기 셋업 완료로 쓰고, 사용자 관찰 대기나 실행 차단은 일부 완료·차단으로 남겨라. 의존성이 필요 없는 구성은 이유와 함께 해당 없음으로 표시하라. 명령 안내·빌드·HTTP 200·로직 통과는 화면 성공을 대신하지 않는다. 셋업 완료 후 로직·예외 검사와 남은 수동 흐름으로 이어가며, 셋업 성공을 전체 업무 기능 완료로 확대하지 마라.
