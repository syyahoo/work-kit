# 변경 상황별 작은 점검

관련 기능이 있을 때만 적용하라. 코드가 없는 동작을 구현된 기능처럼 설명하지 마라. 아래는 사례 선택 기준이며 합격 판정이나 모든 경우를 망라한 목록이 아니다.

| 상황 | 확인할 경계 | 기록할 근거 |
|---|---|---|
| 적용 전 취소 | 기존 상태 유지·임시 데이터 폐기 | 전후 데이터·취소 경로 |
| 적용 도중 취소 | UI·요청·서버·저장의 각 중단 범위 | 중단된 단계·남은 부작용 |
| 저장 후 되돌리기 | 취소와 복구·이전 판본 보존 | 복구 코드·실행 또는 미지원 |
| 중복 실행·재시도 | 화면 방지·서버 멱등성·중복 기록 | 부작용 수·다른 진입점 |
| 실행 중 입력 변경 | 늦은 응답·버전 일치·기존 검증 무효화 | 응답 순서·최종 표시 데이터 |
| 일부 처리 실패 | 원자적 적용·오류 표시·기존 상태 | 실패 시 데이터와 화면 |
| 자원 감소 | 총량·개별 제약·미처리 명시 | 불가능 근거·누락·초과 검사 |
| 입력 증가 | 시간·정확성·화면·메모리 | 실제 크기·환경·측정 결과 |
| 동점·입력 순서 변화 | 정책상 재현성·우선순위 | 정해진 규칙·전후 결과 |
| 새로고침·재시작 | 저장소와 메모리의 경계 | 보존되는 값·사라지는 값 |

- 먼저 핵심 정상 흐름 하나와 변경 영향이 큰 실패 흐름 하나를 선택하라. 나머지는 영향·시간에 따라 추가하라.
- 동시성은 실제 순서 뒤바뀜을 제어하는 검사나 분리 요청으로 확인하라. 단순 이중 순차 호출을 병렬 검증이라 부르지 마라.
- 입력을 생성하면 정책에 맞는 독립 불변조건을 확인하라. 예: 개별 정원 준수, 중복 처리 없음, 처리됨+명시적 미처리의 총합 일치. 구현을 그대로 다시 계산하는 검사만 쓰지 마라.
- 알고리즘 비교는 먼저 같은 필수 제약 충족을 확인하고 같은 입력의 목적값·시간을 비교하라. 일부 입력의 개선을 최적성·보편적 우위로 확대하지 마라.
- 자원 부족·불완전 입력은 명확한 오류나 미처리로 표현할 수 있다. 모든 입력에서 성공 결과를 만들어야 한다고 가정하지 마라.
