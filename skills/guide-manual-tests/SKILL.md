# 수동 테스트 도우미

사람이 해야 할 조작과 화면 왕복을 줄여라. 실제 과제·환경·사용자 지침을 먼저 따르라. 이 문서가 브라우저 제어 권한이나 설치 성공을 제공한다고 표현하지 마라. AI 사용이 금지된 평가 단계에서는 중단하라.

## 공통 시작과 연결

기존 정본의 현재 단계·대기 Q/R/D·다음 행동을 확인하라. 검증 준비가 요구 의미나 설계 선택을 확정하지 않는다. 미확인 R 때문에 기대값을 정할 수 없으면 해당 검사를 보류하고 조건 확인으로 연결하라. 각 T의 대상 R, 관련 D·코드 판본·증거 종류를 연결하고 필수 R의 검사 누락을 마무리에 확인하라. `explain-as-you-build`의 공통 절차가 있으면 따르되 같은 기록을 다시 만들지 마라.

## 현재 범위와 터미널 검사

1. 실제 앱·실행 명령·미리보기 경로·요구·현재 코드·검증을 필요한 만큼 읽어라. 이미 확인한 환경·선택은 다시 묻지 마라. 기존 WORKLOG 등 하나의 정본을 사용하라. `explain-as-you-build`가 사용 중이면 그 정본에 연결하고 보고서를 중복 생성하지 마라.
2. CLI만 있어도 앱 소스를 수정할 수 있으면 앱 내 안내 UI를 구현할 수 있다. 실제 미리보기 접근·렌더링은 별도 확인 사항이다. IDE 분할창·팝업·확장·외부 브라우저·자동 클릭을 전제하지 마라.
3. 기존 검사와 허용된 명령을 먼저 사용하라. 계산·제약·입력 검증·상태 전이·API·저장 로직을 작은 합성 입력으로 검사하고 수동 화면 확인은 잔여 위험에 집중하라. 불필요한 패키지·대규모 테스트를 만들지 마라.
4. 화면 자동 조작이 금지되면 headless를 포함한 Playwright·Selenium·CDP, 클릭·입력 시뮬레이션·콘솔 주입으로 대신하지 마라. 직접 함수·허용된 로컬 API 검사가 화면과 버튼의 검증은 아님을 밝혀라.
5. 실행 0건·전부 skip·실패·옛 코드 결과를 통과로 표시하지 마라. 직접 실행·코드 확인·mock·사용자 관찰·미검증을 구분하라. 같은 로직을 사람이 다시 계산하게 하지 않되 버튼 연결·오류 표시·새로고침 등 미확인 경계는 남겨라.

## 안내 위치의 비교와 선택

기존 선택이 없으면 두 안의 장단점·현재 적합성과 추천을 짧게 제시하고 사용자 선택을 기다려라. 작동을 보장하지 마라. 선택 대기 중에는 읽기·기존 검사·사례 작성만 진행하라.

| 선택지 | 처리 방식 | 장점 | 단점·조건 |
|---|---|---|---|
| 앱 내 접이식 패널 | 앱 소스로 사례·입력·기대·기록을 같은 화면에 표시 | 문서 왕복 감소 예상 | 앱 수정·레이아웃·노출 확인 필요 |
| 채팅 카드 | 한 번에 2~3개 이하의 짧은 사례 제시 | 앱 수정·새 도구 불필요 | 묶음 사이 채팅 전환 필요 |

앱 수정이 불가능하거나 명세와 충돌하면 이유와 실행 가능한 대안을 제시하라. CLI 사용 사실이나 무응답을 패널 선택으로 해석하지 마라. 사용자가 판단을 명시적으로 위임한 범위만 대신 선택하라.

## 최소 사례와 실행 안내

- [사례와 기록 규격](references/cases.md)을 읽어라. 현재 기능에서 정상 흐름 하나와 영향 큰 실패·경계 하나를 먼저 고르고 관련된 나머지만 추가하라.
- 각 사례에 준비 상태·정확한 입력·사람의 조작·기대 화면과 데이터·관찰 기록란·코드 판본을 붙여라. 기대값은 요구나 독립 불변조건에서 도출하라.
- 같은 화면·준비 상태의 항목을 묶고 앞 사례의 데이터 변경을 고려하라. 초기화·샘플 주입은 범위와 보존 방법을 확인하고 사용자 요청 없이 실행하지 마라.
- 느린 처리가 실제 관찰될 때만 수동 취소·중복 요청을 검증할 수 있다고 설명하라. 제어된 터미널 검사·코드 확인을 보완 근거로 남기고 임의 지연·검증 생략을 제품에 몰래 넣지 마라.
- 사용자 관찰을 반영해 다음 묶음을 안내하라. 무응답·화면 전환·시간 경과는 통과가 아니다. 기능을 자동 조작하거나 자동 통과시키지 마라.
- 패널을 선택한 경우에만 [앱 내 안내 패널](references/panel.md)을 읽고 번들 구성품을 현재 앱에 연결하라. 패널 자체 동작과 업무 기능 성공을 구분하라. 실제 미리보기 관찰 전에는 표시 성공을 미검증으로 남겨라.

## 실패·재검사·마무리

- 실패 시 사례 ID·실제 입력·관찰·오류·판본을 확보하고 원인을 좁혀라. AI가 볼 수 없는 화면을 봤다고 쓰거나 사용자 보고에 없는 결과를 채우지 마라.
- 수정 후 같은 조건과 영향받은 이웃 사례만 재검사하라. 기대·입력이 바뀌면 새 기준으로 표시하라. 관련 코드 변경 후 옛 수동 결과는 재확인 필요로 남겨라.
- 마지막에 **터미널 확인 / 사용자 수동 확인 / 실패·차단·재확인 필요**를 짧게 정리하고 정본을 갱신하라. 사용자 관찰을 AI 직접 검증으로 합치지 마라.
- 제출 전 패널 켜짐·꺼짐의 핵심 화면·기본 URL 노출·제출 조건 충돌을 확인하라. 제거해야 하면 import·스타일·라우트도 정리하고 영향받은 검사만 수행하라.
