# 실제 브라우저 출력의 조기 확인

첫 의미 있는 화면이나 핵심 화면 변경 직후에 사용하라. HTTP 200·빌드 성공·단위검사만으로 화면이 정상이라고 표시하지 마라. Docker에서 실행한다면 현재 이미지·코드·포트가 실제 검사 대상인지 먼저 확인하라.

## 1. 규정과 준비 상태를 먼저 확인

- 최신 과제 지침과 제공된 도구에서 **자동 렌더링·화면 캡처**와 **클릭·입력 등의 자동 조작**의 허용 범위를 확인하라. 'Computer Use 금지'만 보고 캡처 전용 검사가 자동 허용된다고 추정하지 마라. 모호하면 제공된 도우미에게 해당 행위를 구체적으로 확인하고, 그동안 IDE Browser에서 사용자가 첫 화면을 확인하도록 안내하라.
- 질문 예: “직접 만든 앱의 로컬 주소를 headless Chromium으로 렌더링하고 콘솔 오류·화면 캡처를 확인하는 읽기 전용 검사가 허용되나요? 자동 클릭·입력은 하지 않습니다.” 실제 답을 받기 전에는 허용 확정으로 쓰지 마라.
- 이미 있는 브라우저 실행 파일과 버전, 허용된 실행 경로·라이브러리·컨테이너 위치를 먼저 확인하라. 없으면 곧바로 Chromium·Playwright를 설치하지 마라. 자동 검사가 허용되고 필요할 때만 지원되는 방법으로 설치·실행하고, 설치/실행 제한을 우회하지 마라.

## 2. 허용된 자동 렌더링 또는 사용자 첫 화면 관찰

자동 렌더링이 명시적으로 허용되고 도구가 준비됐으면 실제 앱 URL·경로에서 로드·렌더링 결과를 확인하라. 자동 클릭·폼 입력까지 허용됐다고 확대하지 마라. 규정상 금지·미확인이거나 도구가 준비되지 않았으면 사용자에게 **실제 포트 / 경로 / 기대 화면 / 볼 항목** 한 묶음만 전달하고 관찰을 기다려라. 예시 주소를 실제 주소로 꾸미지 마라.

확인할 최소 범위:

- 서버가 아니라 실제 앱 페이지가 표시되는가. 빈 화면·로딩 고착·오류 화면·기본 템플릿으로 남아 있지 않은가.
- 필수 제목·핵심 입력·주요 결과 영역이 존재하며, 표·글자·버튼이 잘리거나 겹쳐 사용할 수 없는 상태가 아닌가.
- 허용된 도구에서 관찰할 수 있으면 초기 JavaScript 예외·콘솔 오류·필수 JS/CSS/폰트/이미지 로드 실패를 확인한다. 사용자에게 개발자 도구 접근이 없으면 이 항목은 미확인으로 남기고 일반 화면 관찰로 확인했다고 바꾸지 않는다.
- 이미지가 생성됐다는 사실이 아니라 **실제 캡처를 열어 확인한 내용**을 기록한다. 이미지 열람 기능이 없으면 AI 시각 확인은 미검증이며 사용자가 본 범위만 관찰로 기록한다.

고정 대기 시간만 지나면 성공시키지 마라. 실제 요구한 준비 상태·예상 요소와 합리적인 제한시간을 사용하고, 시간 초과·일부 자산 실패는 그대로 기록하라. Chrome 내부 오류 페이지나 로그인/프록시 화면을 앱 렌더링 성공으로 처리하지 마라.

## 3. 근거와 다음 단계

T ID와 대상 R, URL·경로·표시 영역·소스/이미지 판본·관찰 방법·실제 오류/출력·증거 경로를 기존 정본에 연결하라. 빌드/HTTP 확인, 자동 브라우저 로그, AI의 실제 이미지 열람, 사용자 관찰은 별도 증거 종류다. 도구·정책 때문에 못 확인한 항목을 통과로 합치지 마라.

초기 화면 실패는 해당 변경을 고친 뒤 같은 경로에서 다시 확인하라. 첫 화면 확인 후 계산·API·정합성 검사와 실제 버튼·입력·취소·저장 등의 남은 수동 확인으로 이어가라. 초기 출력이 정상이었다는 이유로 전체 앱 완료를 선언하지 마라. 무관한 로직 변경마다 같은 캡처를 무조건 반복하지 말고 변경 영향을 기준으로 판단하라.
