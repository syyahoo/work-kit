# 최소 사례와 관찰 기록

실제 앱·요구에서 항목을 만들고 해당하지 않는 예시를 강제하지 마라. 프로그램의 입력·상태·출력을 확인한 뒤 값을 채워라. 괄호는 실제 결과가 아니다.

## 사례 한 장

> T ID / 관련 R ID / 관련 D·코드 판본:
> 준비: [초기 화면·데이터·이전 사례의 영향]
> 입력: [구체적인 값 또는 합성 fixture 경로]
> 조작: [사람이 수행할 순서 1~3개]
> 기대: [화면·데이터 불변조건과 요구 근거]
> 관찰: [실제 표시·값·오류, 미보고면 비움]
> 상태: 미실행 / 통과(사용자 관찰) / 실패 / 차단 / 재확인 필요

단순 완료 체크는 관찰 결과가 아니다. '실행함'만으로 통과로 바꾸지 마라. 관찰의 입력·출처·판본이 불명확하면 그 불확실성을 남겨라. 정적 분석·터미널 검증은 별도 증거 종류로 기록하라.

## 관련될 때 선택할 사례

| 후보 | 사람이 볼 경계 | 터미널에서 먼저 확인할 부분 |
|---|---|---|
| 정상 등록·저장 | 입력 → 버튼 → 반영·다시 열기 | 데이터 규칙·직렬화·저장 로직 |
| 잘못된 입력 | 오류 위치·설명·기존 자료 유지 | 경계값·누락·중복 검증 |
| 취소 | 적용 전·진행 중·완료 후 의미 | 요청·커밋·복구 경계 |
| 빠른 중복 실행 | 버튼 상태·중복 결과·피드백 | 중복 요청 부작용·멱등성 |
| 처리 중 입력 변경 | 최종 화면과 현재 입력 일치 | 응답 역전·판본 검사 |
| 자원 부족·규모 증가 | 미처리 안내·대기·화면 반응 | 제약·누락·시간·메모리 |
| 새로고침·재시작 | 저장 상태 복원 | 저장 범위·복구·이전 스키마 |

함수/API 성공이 해당 UI의 수동 통과를 뜻하지 않는다. 규모·시간 수치를 실행하지 않았으면 예측으로만 적어라.

## 정본에 연결할 한 줄

`[사례 ID] 판본 / 증거 종류·출처 / 조건·기대 / 실제 관찰 / 상태 / 수정·재검사`

관련 파일 해시 또는 커밋+미커밋 상태로 판본을 식별하라. 앱에 식별자를 넣지 못하면 묶음 시작 때 기록하고 테스트 중 관련 코드가 바뀌면 영향을 받은 결과를 재확인 필요로 남겨라. 시간·횟수·관찰을 꾸미지 마라.
